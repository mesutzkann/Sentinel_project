# Routing dataset

What the Phase 8 router is trained on and measured against: a question in, the plan it implies
out. Generated by `ai-service/training/routing_dataset.py` from the phrasings in
`ai-service/training/templates.py`; rebuild it with `python -m training.routing_dataset`.

```json
{"id": "R01072", "query": "which class is responsible for the notification sender",
 "language": "en", "source": "template", "template": "which class is responsible for {thing}",
 "intent": "CODE_LOOKUP", "requires_rag": true, "requires_mcp": true,
 "tools": ["source-code-mcp/search_code", "source-code-mcp/read_file"], "target_service": null}
```

| | train | val | test |
|---|---|---|---|
| rows | 1711 | 161 | 333 |
| phrasings per intent | 14–17 | 1 | 3 |

2205 rows over fifteen intents, 933 English, 840 Turkish and 432 deliberately mixed.

## The two things that decide whether it means anything

**It is not written from the rule router's keyword table.** `routing/rule_router.py` matches
`"slow quer"`, `"deadlock"`, `"connection pool"` and forty more terms. A dataset assembled from
those would make the keyword baseline score close to perfect and Phase 8's claim — that a tuned
1.5B beats a keyword table on the questions people actually ask — would be measured against a
straw man. The phrasings are written as questions; the overlap with the rule table is whatever it
honestly is, and the table scores 0.354 on the test split as a result — 0.314 over the whole
dataset, where phrasing luck cannot reach it.

**A phrasing never appears on both sides of the split.** Every fill of one template goes to one
split, so the test set contains phrasings the model has never seen rather than services it has
never seen in a phrasing it knows by heart. Paraphrases inherit their seed's template for the
same reason: a rewrite of a training question is not a test question.

**The floor is per intent *and* language**: one test phrasing for every (intent, language) pair,
plus one validation phrasing per intent. Reserving per intent alone was not enough. The first
Phase 8 build measured mixed-language accuracy at 0.11 — and its test split turned out to hold
eleven mixed rows from two intents, a number too thin to mean anything, hiding a model that had
barely been trained on mixed at all. A language the benchmark cannot report on is a language
nobody fixes. It costs test a little over its tenth, and it is the right thing to spend it on.

The price to know about: **a single hard phrasing now costs an intent-language pair outright.**
Each pair rests on one phrasing worth five to seven rows, so per-language and per-intent numbers
carry real variance — read them as direction, not as decimals. The overall number rests on
forty-five phrasings and holds steady across splits.

## What is in a row, and where it comes from

`intent` and `target_service` are the label. Everything else — `requires_rag`, `requires_mcp`,
`tools` — is derived from `routing/plans.py`, the same table the planner acts on, so a model
trained on this cannot learn a plan the agent would not execute. `tools` therefore follows from
`intent`, and the benchmark's tool F1 tracks intent accuracy closely rather than measuring
something independent.

`source` is `template`, `typo` or `paraphrase`. Typo'd twins are 10% of the rows: one deliberate
slip each — a doubled letter, a dropped one, a transposition, or a Turkish character typed as its
ASCII cousin — because people type badly under pressure and a router that only works on clean
input works in a demo. Paraphrases are produced by a local 7B and filtered mechanically: a
rewrite that loses the service name or changes language is dropped, because it inherits the
seed's label and a drifted rewrite is a mislabelled row. Asked to rewrite "was orders touched
before this started", the 7B returned Turkish, about conditional payments; both filters caught
it.

## Where the baselines stand

`python -m evaluation.router_eval --split test --models sentinel-router --prompt v2`, on an
RTX 3060 Laptop, 333 questions:

| router | prompt | intent | service | tool F1 | invalid JSON | p50 |
|---|---|---|---|---|---|---|
| rule table | — | 0.354 | 0.976 | 0.410 | 0% | 0 ms |
| `qwen2.5:1.5b-instruct` | v1 | 0.162 | 0.453 | 0.150 | 0% | 1213 ms |
| **`sentinel-router`, QLoRA on this set** | v2 | **0.871** | 0.964 | 0.726 | 0% | 1241 ms |

The tuned 1.5B is two and a half times the keyword table at the thing the phase is judged on, and
eight intents of the fifteen are perfect. It is short of the roadmap's 0.95, and the shortfall is
six phrasings rather than a diffuse weakness — see below.

**These numbers are not comparable with the first build's 0.449 and 0.693.** That build was
measured on a test split drawn per intent rather than per intent and language; this one holds a
phrasing the model has never seen for all forty-five pairs, and the keyword table drops from
0.449 to 0.354 on it without a line of its code changing. The earlier model cannot be re-measured
here either: it trained on phrasings this split now tests with.

### What the second build fixed, and how

Everything that moved was data. The first build's three weak spots were measured, not guessed,
and each had a cause in the dataset rather than in the model:

| | first build | now |
|---|---|---|
| `mixed` language | 0.11 | 0.87 |
| `PERFORMANCE_ANALYSIS` | 0.13 | 0.90 |
| `TRACE_QUERY` | 0.22 | 0.60 |
| p50 latency | 2482 ms | 1241 ms |

- **Mixed was one phrasing per intent.** With the split reserving three phrasings per intent for
  val and test, several intents had their only mixed phrasing reserved away — the model was never
  trained on mixed for them at all. Four per intent now, and no intent-language pair is missing
  from training.
- **Six phrasings were labelled against the plan table.** "Find the slowest spans", "where does a
  checkout spend its time" sat under `TRACE_QUERY`, but `traces-mcp/get_slowest_spans` is
  `PERFORMANCE_ANALYSIS`'s tool in `routing/plans.py`. The model was being marked wrong for
  reading them the way the planner does. They moved to the intent whose tools they ask for.
- **Latency was the GGUF, not the prompt.** Q8_0 is 1.9 GB against f16's 3.55 GB on a 6 GB card,
  and halves p50 without costing accuracy. Still eight times the 150 ms target; the remaining
  lever is the model, not the quantisation.

### Where the last 13% is

Thirty-three wrong answers, from **six phrasings**. One test phrasing per intent-language pair
means one hard phrasing takes a pair to zero, so the failures are concrete enough to quote:

| label | read as | phrasing |
|---|---|---|
| TRACE_QUERY | LOG_QUERY | "gateway servisi için log satırı değil iz istiyorum" |
| FULL_INVESTIGATION | ERROR_ANALYSIS | "60 dakikadır gateway için alert geliyor, ne oluyor" |
| FULL_INVESTIGATION | TRACE_QUERY | "users yüzünden her yer etkilendi, ne olduğunu çöz" |
| CODE_LOOKUP | REMEDIATION_QUESTION | "gateway yeniden denemeyi nasıl yapıyor göster" |
| CODE_LOOKUP | SERVICE_TOPOLOGY | "which class is responsible for payment authorisation" |

The first is the instructive one: it was written *to* sharpen the TRACE/LOG boundary, and the
model keyed on "log satırı" and dropped the "değil". A 1.5B missing a negation is a fair thing
for a 1.5B to miss. The rest are genuinely ambiguous questions — "how does it do retries" is a
request for code or for a fix depending on who is asking — and Turkish is now the weakest
language at 0.77 against English's 0.98, which is where the next round of data should go.

Three things a tuned model has to answer for:

- **The keyword table is still ahead on services** (0.976 against 0.964), because naming a service
  is a word match rather than a judgement. The intent is the half that needed a model.
- **Invalid JSON is 0% with the grammar on**, which is what ships. The base model produces the
  schema at all only because of that grammar — without it, it was 100% invalid — and that gap is
  what fine-tuning is for.
- **Latency is halved and still wrong.** 1241 ms against a 150 ms target. The prompt is one line
  and the weights are quantised; what is left is a smaller model or a different serving path.
